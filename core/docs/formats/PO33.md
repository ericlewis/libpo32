# PO-33 / PO-133

[Format overview](../PO_FORMATS.md) · [Documentation](../README.md)

The PO-133 uses the same codec family here. Teenage Engineering describes it
as [based on the PO-33](https://teenage.engineering/products/po/capcom), and its
[guide](https://teenage.engineering/guides/po-133/en) documents the same sampler
controls and effect list. The supplied PO-133 bank validates with the shared
decoder: 3,357 packets, sixteen full patterns, 510-byte settings, and 52 sound
headers referencing eight owned pools. This is captured-format compatibility,
not proof of identical firmware or every playback behavior. The physical FX
and control experiments in these guides used a PO-33, not a PO-133.

See the [sampler workflow](../guides/PO33.md) for WAV editing and the
[PO-33 API](../api/PO33.md) for record codecs. The
[effects and retained-state guide](PO33_EFFECTS_STATE.md) contains the related
hardware observations and unresolved state rules.

## Record layout

A standalone melodic sound frame can omit settings, patterns, and other sound
selectors. A 5.85-second transfer containing BEGIN, one SOUND_SELECT, 68
SOUND_DATA packets and END was accepted by a PO-33. It retargeted a known sound
to physical Sound 4; the user confirmed correct playback there and retained
playback of omitted Sound 1. No baseline/readback byte comparison was made for
this experiment. The C sound-transfer API emits this partial-frame shape using
the established insertion layout.

The subsequent standalone C builder → POKit → app path generated Sound 1 from
PCM with no source bank; the user also reported success on the PO-33.

Tags: settings `7D5C`; pattern selector `A041`, data `C498`; sound selector
`68B5`, data `EF78`. Logical records can span several packets. Preserve the
original packet boundaries when reproducing a captured frame.

Settings record: 510 bytes.

| Offset | Bytes | Meaning |
| ---: | ---: | --- |
| 0 | 255 | Raw prefix; fixed byte pattern in the inspected corpus |
| 255 | 128 | Stored pattern-chain slots, including unused entries |
| 383 | 1 | Active chain length |
| 384 | 1 | Tempo |
| 385 | 1 | Raw swing amount |
| 386 | 16 | Retained state; first two coordinates have observed pattern/FX-position associations, full meaning unresolved |
| 402 | 108 | Raw suffix; fixed byte pattern in the inspected corpus |

Pattern record: 1032 bytes. Steps and sound indices below are zero-based.

| Offset | Bytes | Meaning |
| ---: | ---: | --- |
| `48*step + 3*sound` | 3 per cell | Parameter word, 16 x 16 cells; observed roles below |
| `768 + 16*step + sound` | 1 per cell | Note/key-related low nibble; timing-related high nibble, with melodic length and drum retrigger contexts; exact units unresolved |
| 1024 | 8 | Two FX codes per byte, high nibble first in step order; `6` is octave-up, other effect IDs unresolved |

For zero-based step `s`, its FX code is
`(footer_raw[s / 2] >> ((s & 1) ? 0 : 4)) & 15`. This defines storage order,
not the duration or cross-step behavior of each effect.

## Pattern parameters and controls

For a little-endian word `W`, these chunks are useful descriptive coordinates,
not a declaration that four six-bit parameters are the final encoding.

| Chunk | Extraction | Role and evidence | Remaining limit |
| --- | --- | --- | --- |
| q0 | `W & 63` | Observed pitch control: 13 to 7 lowers playback by about six semitones; 17 to 18 raises it by about one | Full scale, neutral value, width and interaction with the control-note nibble |
| q1 | `(W >> 6) & 63` | Observed level control: repeatable gain-like changes; independent intermediate values also occur without a control event | Exact gain curve and zero/retain behavior |
| q2 | `(W >> 12) & 63` | Observed filter control: frequency-dependent playback changes; cutoff is the leading interpretation | Exact filter mapping and numeric units |
| q3 | `(W >> 18) & 63` | Independently varying stored data; resonance is a candidate | No resolved playback effect in the two tested contexts; identity and activation remain open |

Reanalysis of existing no-FX playback covers q0 values 7..22 at control `fc`
and supports approximate semitone ordering across that interval. It does not
establish an exact static conversion. With q0=13, the other chunks fixed at
32/63/32 and identical sample bytes, repeated events in a chained capture form
frequency groups near 219.13 and 219.99 Hz after lower and higher preceding
q0 values respectively. The separation survives shifted windows and spectral
and cycle-period estimates. Pattern identity and FX position also co-vary, so
this is a playback-context association, not a proven smoothing or quantization
algorithm.

A stored control change `fc -> f0`, with sample and parameter words unchanged,
accompanies a shorter event with roughly threefold late-event frequency in
one comparison. A strong onset transient and a recording sync-mode difference
prevent treating that ratio as an exact semitone or key-number conversion.

The physical knobs change function with the edit mode selected by FX. The
[PO-33 guide](https://teenage.engineering/guides/po-33/en) documents these
controls and identifies TONE/FILTER as lockable parameters:

| Mode | Knob A | Knob B | Corresponding storage evidence |
| --- | --- | --- | --- |
| TONE | Pitch | Sound volume | q0 has pitch behavior; q1 has gain-like behavior |
| FILTER | High-/low-pass filter | Resonance | q2 has filter-like behavior; q3 as resonance is unconfirmed |
| TRIM | Sound start | Sound length | Sound-header range coordinates, not another per-step q field; exact UI conversion remains unresolved |

Holding a lit step in WRITE mode is a separate editing context. The
[extended control guide](https://cubeleco.blogspot.com/2019/05/po-33-ko-hidden-features.html)
describes knob A as note/slice selection, knob B as melodic note length, and
held-step plus BPM as drum retrigger selection. These UI operations must not
be confused with TONE/FILTER knob automation or TRIM coordinates.

That guide also reports that holding a step copies its note/slice and parameters
into the defaults used for new steps. It reports delayed trim saves and an edit
page returning to TONE without refreshed icons after sound selection or playback.
These are author observations, not decoded field assignments. They are potential
confounders for control experiments: distinguish a held-step edit from a knob
lock, explicitly select the intended page, and verify settled backup differences
before assigning a parameter or slot-default field.

These are control functions and observed storage roles, not a calibrated
conversion from displayed knob values. For example, q1 `32 -> 41` gave about
`+2.77 dB` in one repeatable noise test with an exact bank readback; another
stimulus/recording workflow gave about `+1.61 dB`. Neither supplies a universal
gain law. q2 `47 -> 63` changed the spectral response without establishing a
cutoff in Hz. q3 `26 -> 30` at q2 `7` survived an exact readback, but did not
produce a resolved playback difference. The resonance identity remains open.
Trim start/end coordinates likewise do not establish a knob scale, a direct
stored-length field, or inclusive/exclusive endpoint behavior.

Raw bit 5 is zero in the inspected corpus. Both 6+6+6+6 and 5+7+6+6 layouts
fit; regrouping as 5+7+7+5 also remains possible. Signedness and field boundaries
must not be inferred from the chunk names alone. Each q extraction yields
0..63 by construction; this is not proof of the physical knob's range or a
six-bit field boundary.

Parameter words with zero control are meaningful stored data. Frekvens has a
pattern with 15 q1-only cells and every control byte zero; other intermediate
values match neither neighboring nonzero-control event. Escalate also stores
nonzero q3 on zero-control rows. Preserve these rows: nonzero word does not
establish a note trigger, and zero control does not establish an empty pattern.
These observations do not by themselves prove runtime hold or interpolation.

The old note/Param B control captures leave the three-byte word unchanged and
vary low/high control nibbles. Some nominally adjacent captures also change
pattern selection, tempo, swing or a second event. They are not isolated q3
sweeps or evidence for a nonlinear joint parameter encoding. Their labels do
not by themselves establish calibrated knob values. The held-step editing
context explains why note and melodic timing edits can affect control nibbles
without changing q0..q3. Similarly, A/B/A in
measurement descriptions names comparison variants, not the two physical knobs.

For the comparisons below, `q0 = W & 63`, where `W` is the little-endian
event word. This is a descriptive coordinate, not a proven field width.

The archived `factory`-labelled capture also has q0=14 on a zero-control row
between two q0=13 control events (pattern 6, sound 9, steps 12..14). Thus
copying either adjacent control event cannot explain all stored q0 values.
The capture label does not independently authenticate factory provenance.

Four captured banks contain controls `fc`, `1c`, `10` and `f0` at pattern 0
offset 768, with every other logical byte identical. This establishes that
the two nibbles can vary independently over those observed combinations.
Six other matched pairs retain word `0d f8 83` and controls
`19`, `29`, `39`, `49`, `69`, `89` when relocated between steps 6 and 15,
sound 8 (zero-based). Moving only the word and control produces the entire
counterpart bank exactly. The stored codes therefore do not require a
step-dependent lookup for those two positions; audible repeat counts remain
unverified.

The high-nibble datasets cover different sound contexts: the melodic edits are
on sound 0, while the drum retrigger edits are on sound 8. Complete word/control
combinations also occur in both melodic and drum slots. Consequently, the raw
timing nibble is not a universal duration or repeat count; sound context must
accompany a musical interpretation. The structural codecs preserve both nibbles
without inventing a key-number, note-length or retrigger conversion.

Capture names are experiment labels, not calibrated values. Two differently
labelled note captures contain identical banks in distinct source-audio files.
Historical label-based note maps and retrigger ordinals must not be exposed
as verified key, pitch or repeat-count conversions.

## Sample pools, ranges and copy behavior

Sound header: nine bytes: LE32 range start, LE32 range end, source selector.
These are raw coordinates: inclusive/exclusive conventions and all range
constraints remain unresolved. Populated pools contain following mu-law bytes
in 4096-byte blocks. Copy/slice entries may have only a header and refer to
another pool. Typically selectors 0..7 are melodic; 8..135 form eight groups
of sixteen drum slices. Copy operations can reference a different group's
source. Stored ranges can exceed the received allocation; encoders preserve
these values without clamping them.

A source selector refers to the entire stored pool, not its owner's trimmed
range. Aliases can extend outside that owner's range, and a drum group can
contain multiple owned pools. Direct low-nibble slice indexing fits inspected
official patterns better than XOR 12 under an audible-slice assumption, but
other mappings survive; no exact key-to-slice map is exposed here.

Two clean comparisons in an archived copy series support shared sample storage.
One fills a previously empty melodic selector with only a nine-byte header
`(start=0, end=246720, source=0)`. The next fills drum selectors 8..23 with
sixteen header-only references to the same source. All settings, all sixteen
patterns, existing sound records and the complete 249,856-byte pool remain
identical across each comparison. Fresh decoding reproduces the three complete
frames with 1,274, 1,275 and 1,291 valid packets respectively. The selector
packets already existed; these operations add associated sound data, not new
selector identities.

For that drum copy, zero-based slice `i` has end `15420*(i+1)` and start zero
for the first slice, otherwise `15420*i+1`. The last end matches the source
header's end rather than the pool allocation. This supports regular subdivision
in this zero-start, divisible-span example; alone it does not establish
nonzero-start arithmetic, remainder rounding or endpoint inclusion. A separate
drum capture has unequal ranges with `next_start == previous_end`, so the copied
series' one-code boundary difference is not a universal range constraint. The
preceding source-to-first-copy comparison also changes audio and allocation and cannot
isolate copy behavior. All copy-series patterns are empty, leaving the extended
guide's claim that destination tone/filter settings survive copying untested.

A controlled PO-33 copy on 2026-11-05 extends that evidence to a nonzero start
and a span not divisible by sixteen. The baseline readback retains source
range `(257,33028)` and its 45,056-byte pool, with drum selectors 8..23 empty.
Copying melodic Sound 1 to drum Sound 9 fills only those sixteen selectors
with nine-byte headers referencing source 0. Every other logical record,
including settings, all patterns and the source pool, remains byte-identical.
The before/after transfers validate 423 and 439 packets; both recordings have
zero reported dropped frames or sample-time gaps.

For this copy, all sixteen ranges satisfy the following coordinate rule,
where `S=257`, `E=33028`, and `i=0..15`:

```text
end(i)   = S + floor((E - S) * (i + 1) / 16)
start(0) = S
start(i) = end(i - 1) + 1, for i > 0
```

This distinguishes flooring each boundary from truncating one shared stride
or rounding boundaries to nearest. The sixth end is 12,546 and the final end
is 33,028; a truncated stride would yield 12,545 and 33,025. The same rule fits
the archived divisible-span copy. These two cases constrain copy-generated
coordinates, not every source length, internal arithmetic or audible endpoint
inclusion. The baseline is the actual readback: an initial key tap had also
changed one pattern step before copying, and that step remained unchanged
across the copy comparison.

An editor must distinguish replacing a shared pool from replacing one slot or
slice: every reference to an edited pool can be affected. These captures do not
establish pool reclamation after deletion, detaching a single alias, or how an
empty selector affects an already populated receiver slot.

Escalate's out-of-allocation references belong to a sound unused by all its
patterns. Retained earlier ranges are plausible, not established. This does
not justify clamping, wrapping or halving coordinates. Nonzero samples can
occur outside trims and at touching endpoints; silence is not a universal
boundary marker and does not settle inclusive versus exclusive ends.

For populated pools, the first 4,096 sample bytes and nine-byte header are
packetized as sixteen 255-byte payloads followed by 25 bytes. Each additional
4,096-byte block uses sixteen 255-byte payloads followed by 16 bytes. The hosted
editor retains original packets and follows this layout when appending blocks.
It keeps all nine header bytes and all reference headers unchanged, padding
short replacements with silence rather than shrinking the original allocation.
The original trim can therefore hide appended audio. The one-block growth
case below has an exact physical readback; maximum device storage capacity and
general acceptance of larger allocations remain unverified.

The [PO-33 guide](https://teenage.engineering/guides/po-33/en) advertises 40
seconds of recording memory. Escalate's sixteen owned pools serialize 987,136
companded sample bytes, or about 42.12 seconds at the nominal sample clock.
Stored pools include block padding and can extend beyond their trims, so the
advertised recording time cannot be used as a hard limit on backup sample bytes.
The [capacity observations below](#capacity-observations-and-failed-restores)
establish a retained-storage result and nearby failures for specific scratch
banks; the general device allocation rule and limit remain unresolved.

Across three official PO-33 packs, `(last_nonzero_code_index + 1) - raw_end`
equals 576 in 18 of 21 owned melodic pools. Two others give 574 and one gives
-205; all four melodic pools in the supplied PO-133 reference give 100. This
calculation treats both `00` and `ff` as zero codes; neither marks a verified
playback endpoint. The repeated content relationship is not a universal guard
length or endpoint rule. Retain the full pool instead of inferring its
allocation from the trim or last nonzero code.

`po33_settings_*`, `po33_pattern_*` and `po33_sound_header_*` provide structural
codecs. They preserve raw fields; they are not a complete sequencer or editor.

### Sample replacement hardware validation

On 2026-11-06, two short scratch-bank transfers generated by
`po33_encode_capture` through the core pool transaction APIs were loaded onto
one PO-33. Both showed `End`. Each bank was then sent back by the device,
decoded with every packet checksum validated, and compared byte-for-byte with
its generated frame:

| Case | Converted sample bytes | Pool allocation before → after | Packets | Frame bytes |
| --- | ---: | ---: | ---: | ---: |
| Replacement within allocation | 28,125 | 45,056 → 45,056 | 423 | 68,450 |
| Growth by one block | 46,875 | 45,056 → 49,152 | 440 | 72,631 |

Both inputs were mono PCM16 WAVs at 44,100 Hz, converted to the nominal sample
clock; transfer WAVs used 48 kHz stereo. The returned frames exactly preserved
the new sample data and padding, nine-byte header, all sixteen patterns,
settings and metadata. The growth case retained one additional 4,096-byte block
and its seventeen data packets. Trim and source references were unchanged.

Interrupted readbacks were retained as failed evidence and retried. The
successful readback recordings also had interface timing resets after the
complete modem bursts, so whole-recording continuity did not pass. The complete
frames recovered before those resets validated without byte repair or combining
captures; trailing receiver bytes were excluded from the frame comparison.

These results establish storage and restoration for these two transfers on
that PO-33. They do not establish audible playback, trim endpoint semantics,
maximum capacity, arbitrary pool growth or PO-133 hardware acceptance.

### Full-length replacement hardware validation

Two further PO-33 transfers exercised `po33_sample_edit_plan` and
`po33_sample_edit_rebuild`, which combine replacement and an automatic range
update. Each uses raw start 0, end N for N encoded samples, and silent padding
at coordinate N. The selected pool has no other references.

| Input | Encoded samples / raw end | Allocation before → after | Packets | Frame bytes |
| --- | ---: | ---: | ---: | ---: |
| 0.8 seconds at 44,100 Hz | 18,750 | 45,056 → 45,056 | 423 | 68,450 |
| 2 seconds at 48,000 Hz | 46,875 | 45,056 → 49,152 | 440 | 72,631 |

Both transfers showed `End`. Complete device readbacks matched their generated
frames byte-for-byte, including fitted ranges, sample bytes, guard/padding,
source selector, settings and all patterns. Both successful readback recordings
had zero timestamp gaps, dropped frames or overloads. Earlier interrupted or
silent attempts were retained separately and contributed no successful result.

Each source contains three ascending tone cues near its beginning, middle and
end. The user heard all three on both replacements; continuous playback
recordings also contain the expected three pitches, approximately 659, 1,319
and 1,978 Hz. The common pitch ratio is about 1.5 relative to the source, so
nominal source duration must not be confused with audible playback duration.
The longer sample's final cue starts at source time 1.82 seconds, beyond the
old raw end of 33,472 (about 1.43 nominal seconds), and is present in playback.

This supports practical full-content replacement for these two inputs on one
PO-33, including extension beyond the old trim. The silent guard and terminal
silence intentionally leave inclusive/exclusive endpoint behavior unresolved.
These tests do not establish maximum storage, arbitrary growth, shared-pool
resizing, exact audible duration, or PO-133 physical compatibility.

### Empty-slot insertion and packet boundaries

A further PO-33 probe added a new owned pool to previously empty melodic
Sound 2 (selector 1), while preserving Sound 1, all settings and patterns.
The new pool contains 14,063 encoded samples, a silent guard and padding to
16,384 bytes, with header `(start=0, end=14063, source=1)`.

An initial transfer used consecutive 255-byte data packets across allocation
boundaries. It passed software framing and modem checks and showed `End`, but
its complete device readback had altered samples near the starts of later
blocks. The first 4,096 samples and every unrelated logical record matched.
The affected regions corresponded to the input packet portions crossing each
allocation boundary. Thus valid wire checksums and equal concatenated record
bytes are insufficient evidence that arbitrary rechunking is hardware-safe.

The corrected transfer terminates packets at every allocation-block boundary.
The first block contains the nine-byte header plus 4,096 samples, emitted as
sixteen 255-byte packets and one 25-byte packet. Each later block uses sixteen
255-byte packets and one 16-byte packet. This matches the device's observed
output layout. Its 508-packet, 89,364-byte hardware readback was byte-identical
to the generated reference. The reusable core insertion API reproduces that
same frame exactly.

The user heard the new two-cue sample and then the preserved three-cue Sound 1.
Continuous recordings confirm the expected two-tone and three-tone sequences;
successful readback and playback recordings have no timestamp gaps, dropped
frames or overloads. The failed crossing-packet candidate remains separate
counterexample evidence. This establishes one melodic-slot insertion on one
PO-33, not drum-slice construction, arbitrary empty-bank topology, maximum
capacity or PO-133 receive behavior. Existing captured packet boundaries should
still be preserved rather than normalized to this one observed layout.

### Copied melodic sound detachment

A PO-33 Sound 1-to-Sound 2 copy produced a complete 441-packet, 72,645-byte
baseline. Sound 1 owned a 49,152-byte pool; Sound 2 contained only its nine-byte
header, referencing source selector 0 with the same raw range `0..46875`.
Both sounds therefore resolved to one shared pool.

The core detachment transaction replaced only Sound 2's alias data with a new
16,384-byte pool containing 14,063 encoded samples and padding. Its new header
uses source selector 1 and range `0..14063`. All 440 original packets outside
the replaced alias data matched in payload and relative order. Sound 1's full
header and sample bytes, all settings and every pattern also matched the
captured baseline independently.

The generated transfer showed `End` and its complete hardware readback matched
all 508 packets and 89,364 frame bytes exactly. The user heard Sound 2's new
two-cue sample followed by Sound 1's preserved three-cue sample. Continuous
recordings contain the expected two-tone and three-tone sequences; both the
readback and playback recordings have zero timestamp gaps, dropped frames or
overloads. The baseline and candidate bytes remain distinct evidence of the
shared-to-independent transition, rather than just a new empty-slot insertion.

This verifies one header-only melodic alias replacement on one PO-33. It does
not establish relocation of a shared pool's owning record, drum-slice
detachment, general storage capacity or PO-133 hardware compatibility. The
replacement range follows the existing guarded policy; endpoint inclusion and
exact audible duration remain unresolved.

### Capacity observations and failed restores

Core accounting counts owned pools once, independently rounds each pool to
4,096 bytes, and reports aliases without adding their source audio again.
Serialized sample data includes padding and audio outside trims. Transfer
framing, headers, settings and patterns belong to the separate wire-size
count. Neither count alone describes all possible firmware memory costs.

One PO-33 was tested with large scratch pools containing low-level markers
outside short playable ranges. All generated candidates passed software modem
verification. The observed outcomes were:

| Blocks | Sample bytes | Pools | Receive observation | Complete readback |
| ---: | ---: | ---: | --- | --- |
| 241 | 987,136 | 1 | End | Exact 1,030,080-byte frame |
| 242 | 991,232 | 1 | Err | 241 blocks with the new probe marker |
| 244 | 999,424 | 1 | Normal screen; neither End nor Err observed | Byte-identical to the earlier 241-block bank |
| 244 | 999,424 | 2 | Err | Not collected |
| 248 | 1,015,808 | 1 | Err | Not collected |
| 248 | 1,015,808 | 2 | Err | Not collected |
| 256 | 1,048,576 | 1 | Err | Not collected |

The 241-block bank's entire sample pool and all other frame bytes survived
receive/SEND exactly. This is a verified retained-storage result, not proof
of a greater-than-advertised playable recording duration. The 244-block
single-pool candidates shared the accepted bank's prefix, so that readback
alone could not distinguish old-bank retention from partial loading.

The 242-block probe added a distinct marker within that common prefix. After
`Err`, the device returned a complete 241-block bank containing that new marker.
Only the marker's 16 sample bytes differed from the earlier accepted logical
records; the recording had no timestamp gaps, missing/dropped frames or
overloads. **A failed receive can modify stored sample data: Err is not a
rollback guarantee.** The core's transactional output guarantees concern
software buffers, not the device's receive behavior.

This establishes an observed adjacent success/failure for one-pool scratch
banks and shows that splitting the failed 248-block total did not make it
acceptable in that trial. It does not prove a universal 241-block maximum:
pool bookkeeping, record layout, transport effects, recording-time limits and
PO-133 behavior remain distinct questions. Keep a known-good backup before
transferring edited banks, and verify complete readback rather than relying
solely on the display or a sample-byte budget.
